1. src/clean.py
----------------------------------------------------------------------

Source-code facts:

- clean() connects to SQL Server using SQLSERVER_CONNECTION.
- It operates in place on stg.reports, stg.drugs, and stg.reactions.
- Invalid or out-of-range receivedate values are quarantined and the
  corresponding report rows are deleted.
- receivedate must parse from the first eight characters as YYYYMMDD.
- Dates before 1900-01-01 or after the machine's current date are rejected.
- patientonsetage is converted using unit codes:
    800 = months
    801 = years
    802 = weeks
    803 = days
    804 = hours
- Ages below 0 or above 120 years are set to NULL, along with the age unit.
- patientweight values <= 0 or > 500 are set to NULL.
- Invalid numeric weight values are treated as invalid and set to NULL.
- Older versions are removed by keeping MAX(safetyreportversion) for each
  safetyreportid.
- Orphaned staging drug and reaction rows are deleted after report-version
  deduplication.
- The function records quarantine rows and quality-log rows.
- Missingness is measured for patientsex, patientonsetage, patientweight,
  primarysourcecountry, occurcountry, and companynumb.
- The function writes results/data_quality.json.

Important behavior:

- The cleaning step mutates staging data. It is not a read-only query
  service and should not be called from a web request.
- Missing values are generally retained as NULL after cleaning, not filled
  with user-facing defaults.
- The code uses today's date at execution time, so reproducibility of the
  date-range rule depends on the run date.

Application implication:

- A new user-entered report can be validated with similar rules, but that
  does not mean it can be inserted into the warehouse safely.
- The cleaning functions are private helpers and are not currently exposed
  as a report-validation service.

static/sentinel dimensions, reads cleaned staging rows, and creates facts.

Report mapping:

    -> fact_report.safetyreportid

stg.reports.safetyreportversion
    -> fact_report.safetyreportversion

stg.reports.reporttype
    -> fact_report.report_type

stg.reports.serious == "1"
    -> fact_report.is_serious = 1

stg.reports.duplicate == "1"
    -> fact_report.is_duplicate = 1

stg.reports.receivedate
    -> fact_report.date_key

stg.reports.receiptdate
    -> fact_report.receipt_date_key

stg.reports.transmissiondate
    -> fact_report.transmission_date_key

stg.reports.primarysourcecountry
    -> fact_report.country_key through dim_country

stg.reports.occurcountry
    -> fact_report.occur_country_key through dim_country

sender and primary-source reporter fields
    -> dim_reporter
    -> fact_report.reporter_key

stg.reports.patientagegroup
    -> dim_age_group
    -> fact_report.age_group_key

stg.reports.patientsex
    -> fact_report.sex_code

stg.reports.patientonsetage plus patientonsetageunit
    -> fact_report.onset_age_years

stg.reports.patientweight
    -> fact_report.weight_kg

stg.reports.companynumb
    -> fact_report.companynumb

Important implementation detail:

The INSERT tuple in transform.py passes dk for both date_key and the
receive_date_key position, while rdk is passed for receipt_date_key.
The source names are therefore important: date_key is based on receivedate,
receipt_date_key is based on receiptdate, and the receive_date_key value
currently receives the same receivedate key. This should be confirmed
against the intended semantics before exposing date filters.

Drug mapping:

- The preferred normalized drug identity is openfda_generic_name.
- Fallback order is activesubstancename, then medicinalproduct, then
  UNKNOWN.
- The normalized drug_name is trimmed, uppercased, and limited to 512
  characters.
- generic_name, substance_name, brand_name, manufacturer_name,
  dosage_form, and route are stored in dim_drug.
- drugcharacterization == "1" becomes fact_drug.is_suspect = 1.
- drugauthorizationnumb and drugindication remain on fact_drug.

Reaction mapping:

- reactionmeddrapt is trimmed and uppercased.
- Missing reaction names become UNKNOWN.
- reactionmeddrapt maps to dim_reaction.reaction_meddra_apt.
- reactionoutcome maps to fact_reaction.outcome_code.

Data types from the schema:

- fact_report.is_serious and is_duplicate: BIT.
- fact_report.sex_code and report_type: VARCHAR.
- fact_report.onset_age_years and weight_kg: DECIMAL(8,2).
- fact_report date and dimension keys: INT.
- fact_drug.is_suspect: BIT.
- Dimension labels and names: VARCHAR with lengths defined in
  sql/02_star_schema.sql.

Missing-value behavior:

- Missing dates map to the -1 dim_date sentinel.
- Missing country codes map to the XX/-1 unknown country sentinel.
- Missing age groups map to age_group_key -1.
- Missing age and weight remain NULL on fact_report.
- Missing sex remains NULL in fact_report, later displayed as unknown in
  some views.
- Missing drug/reaction values become UNKNOWN dimension members.
- Missing reporter fields are normalized to empty-string components for
  reporter lookup.

Classifier feature availability:

The following features are directly represented in fact_report or related
dimensions:

- onset_age_years: fact_report, nullable DECIMAL(8,2)
- weight_kg: fact_report, nullable DECIMAL(8,2)
- sex_code: fact_report, nullable VARCHAR(10)
- report_type: fact_report, nullable VARCHAR(10)
- country_code: dim_country.iso2_code through fact_report.country_key
- reporter_qualification: dim_reporter.qualification through reporter_key
- report_year: dim_date.year through fact_report.date_key
- report_month: dim_date.month through fact_report.date_key
- drug_count: count of distinct fact_drug.drug_key for a report
- suspect_drug_count: count of distinct suspect fact_drug.drug_key
- reaction_count: count of distinct fact_reaction.reaction_key for a report

Can a new user-entered report provide these features?

Partially.

- Age, weight, sex, report type, country, reporter qualification, and
  date can be collected in a form.
- Drug count, suspect-drug count, and reaction count require either a
  structured list of drugs/reactions or an existing database report.
- A user-entered report would not naturally have a trustworthy report year
  and month unless the application defines whether these mean event date,
  receivedate, or current submission date.
- The model was trained on database-derived counts and categorical
  encodings. A new form must reproduce those semantics exactly.

The safer first application design is to support predictions for an
existing selected report, or to clearly label a new-report prediction as
an estimate based on user-supplied feature values.

3. sql/02_star_schema.sql
----------------------------------------------------------------------

Primary keys:

- dim_date.date_key
- dim_country.country_key
- dim_age_group.age_group_key
- dim_drug.drug_key
- dim_reaction.reaction_key
- dim_reporter.reporter_key
- fact_report.report_key
- fact_drug.drug_key (fact-row identity)
- fact_reaction.reaction_key (fact-row identity)

Foreign keys:

fact_report:

- date_key -> dim_date.date_key
- receipt_date_key -> dim_date.date_key
- receive_date_key -> dim_date.date_key
- transmission_date_key -> dim_date.date_key
- country_key -> dim_country.country_key
- occur_country_key -> dim_country.country_key
- reporter_key -> dim_reporter.reporter_key
- age_group_key -> dim_age_group.age_group_key

fact_drug:

- report_key -> fact_report.report_key
- drug_key_dim -> dim_drug.drug_key

fact_reaction:

- report_key -> fact_report.report_key
- reaction_key_dim -> dim_reaction.reaction_key

Relationship grain:

- fact_report is one row per retained safety report version.
- fact_drug is potentially many rows per report.
- fact_reaction is potentially many rows per report.
- A report can contain multiple drugs and multiple reactions.

Join-duplication risk:

Joining fact_report to fact_drug and fact_reaction in the same query
creates a many-to-many multiplication:

    one report x two drugs x three reactions = six joined rows

Therefore, COUNT(*) and SUM(is_serious) are unsafe in a combined
fact_drug/fact_reaction join unless the query first aggregates or uses
distinct report-level logic.

Safe counting patterns:

All reports:

    COUNT(DISTINCT fr.report_key)

Serious reports after a drug join:

    COUNT(DISTINCT CASE WHEN fr.is_serious = 1 THEN fr.report_key END)

Drug/reaction pair candidates:

- Deduplicate report/drug with SELECT DISTINCT report_key, drug_key_dim.
- Deduplicate report/reaction with SELECT DISTINCT report_key,
  reaction_key_dim.
- Join those deduplicated sets on report_key.
- Count DISTINCT report_key for the pair.

This is the pattern implemented in sql/04_signal_views.sql.

Safe aggregation alternative:

- Aggregate fact_drug to report/drug grain before joining report-level
  results.
- Aggregate fact_reaction to report/reaction grain before joining.
- Never sum a report-level seriousness flag after a raw drug/reaction
  many-to-many join.

Parameterized filtering requirement:

The existing views are fixed, non-parameterized SQL Server views. A web
application cannot pass parameters directly into them. The application
needs new parameterized SELECT statements or stored procedures that apply
validated filters before aggregation.

Required filter implementation:

Date:
- Filter using an explicitly chosen fact_report date relationship.
- The application must define whether date means date_key/receivedate,
  receipt_date_key/receiptdate, receive_date_key, or transmission date.

Drug:
- Filter through fact_drug and dim_drug.
- Use a report-level EXISTS predicate or a distinct report subquery when
  the output is report-based.

Reaction:
- Filter through fact_reaction and dim_reaction.
- Use EXISTS or a distinct report subquery to avoid multiplying rows.

Country:
- Choose primary-source country_key or occur_country_key explicitly.
- Join to dim_country and filter iso2_code.

Seriousness:
- Filter fact_report.is_serious directly.
- For percentages, calculate numerator and denominator after all filters.

Recommended implementation style:

- Use parameterized pyodbc placeholders.
- Whitelist selectable sort columns.
- Apply TOP or pagination.
- Aggregate at report grain before joining multiple child facts.
- Return both the result rows and filter metadata.

5. sql/04_signal_views.sql
----------------------------------------------------------------------

View: dbo.vw_drug_reaction_pairs

Columns:
- drug_key
- reaction_key
- drug_name
- generic_name
- manufacturer_name
- dosage_form
- route
- reaction_meddra_apt
- pair_count
- drug_total
- reaction_total

Purpose:

Provides the report-level building blocks for a 2x2 table:

- pair_count = a, reports with both drug and reaction
- drug_total = a+b, reports with the suspect drug
- reaction_total = a+c, reports with the reaction
- total_reports = n, supplied separately by signal_analysis.py

Internal logic:

- suspect CTE deduplicates report_key/drug_key_dim and keeps
  is_suspect = 1.
- rxn CTE deduplicates report_key/reaction_key_dim.
- drug_totals counts distinct reports per suspect drug.
- rxn_totals counts distinct reports per reaction.
- The two deduplicated sets are joined on report_key.
- pair_count is COUNT(DISTINCT s.report_key).

Filters supported by the view itself:

- Suspect drugs only.
- No date filter.
- No country filter.
- No report seriousness filter.
- No user-selected drug/reaction filter inside the view.
- The caller can filter the view's returned drug_key, reaction_key, and
  pair_count, as signal_analysis.py currently does for top drugs and
  minimum pair count.

Date-filtered signal requirement:

The current view calculates totals across the entire warehouse. To support
a date range correctly, all three quantities must use the same filtered
report universe:

- filtered pair_count
- filtered drug_total
- filtered reaction_total
- filtered total_reports

A simple outer WHERE on the current view cannot provide this because the
view does not expose report dates and its totals were already calculated.
A new date-aware query or view must apply the date restriction inside each
aggregation CTE.

Country and seriousness filters have the same requirement. The filter must
be applied consistently to suspect pairs, drug totals, reaction totals,
and total report count.

7. src/trend.py
----------------------------------------------------------------------

Source-code facts:

- trend.py connects directly to SQL Server at module import time.
- It groups fact_report by dim_date.year and dim_date.month.
- It produces total_count and serious_count.
- It inserts zero-valued months between the first and last observed
  month.
- It calculates a linear polyfit over the total report count.
- It calculates average receipt-to-receive lag from stg.reports.
- It writes results/trend.json.

Output fields:

- monthly_series:
    year
    month
    count
    total_count
    serious_count
- series_definition
- polyfit_coefficients
- avg_receipt_to_receive_lag_days

Assumptions:

- fact_report.date_key is the intended reporting date.
- Missing months between observed endpoints represent zero reports.
- The latest observed month may be incomplete, which forecast.py handles
  by excluding it.

Interactive reuse:

- The aggregation SQL can be moved into a parameterized service query.
- The existing monthly result shape can be reused for charts.
- The current module-level execution should not be imported by a web
  request because it opens a database connection immediately and writes
  a file.

8. src/forecast.py
----------------------------------------------------------------------

Input:

- Reads results/trend.json.
- Uses monthly_series.
- Excludes the latest observed month in main().
- Uses total_count and serious_count.

Models:

- _seasonal_naive(): requires at least 12 observations.
- _ets(): requires at least 24 observations.
- _sarima(): requires at least 36 observations.

Parameters:

- HORIZON = 12.
- BACKTEST_ORIGINS = 12.
- MIN_TRAIN = 36.
- SARIMA order = (1, 1, 1).
- SARIMA seasonal_order = (1, 0, 1, 12).

Outputs:

- results/forecast.json
- Selected model for each series.
- Backtest results for each successful model.
- Forecast rows containing year_month, predicted_count, lower_95,
  and upper_95.

Backtesting:

- Rolling-origin one-step forecasts.
- Successful folds are evaluated with MAE, RMSE, and sMAPE.
- Negative predictions are clipped to zero.
- The selected model minimizes MAE, then RMSE.

Interactive reuse:

- The individual model functions can accept a user-selected horizon.
- _metrics() and _backtest() can be reused with a selected series.
- A service can query a filtered monthly series and call the existing
  model functions without changing the existing batch workflow.
- A selected date range is possible if the service constructs a complete
  monthly array before forecasting.
- The current batch main() remains unchanged if the new service calls
  lower-level functions directly.

Limitations:

- Forecasting a very short filtered series can fail because of minimum
  observation requirements.
- The current prediction interval is residual-standard-deviation based,
  not a full probabilistic forecast interval.
- The current model-selection logic is based on one rolling-origin setup
  and may be unstable for small filtered subsets.

Recommended application inputs:

    series: "total_reports" | "serious_reports"
    method: "seasonal_naive" | "ets" | "sarima" | "best"
    horizon_months: int
    start_date: date | None
    end_date: date | None
    filters: dict[str, str | int | bool | None]

======================================================================
D. KEY RISKS THAT MUST BE RESOLVED BEFORE CODING
======================================================================

1. Date semantics:

The schema has date_key, receipt_date_key, receive_date_key, and
transmission_date_key. The transform code currently maps date_key from
receivedate, receipt_date_key from receiptdate, and passes the receivedate
key again for receive_date_key. The application must choose and document
one date meaning.

2. Report-count duplication:

Raw fact_drug/fact_reaction joins multiply rows. All application queries
must use distinct report IDs or pre-aggregated report-grain subqueries.

3. Signal date filtering:

The existing signal view totals are global. Date/country/seriousness
filtering requires a new aggregation query that applies the same filter to
all four contingency quantities.

4. Classifier input design:

The model needs 11 features, including three child-fact counts. Decide
whether users predict existing reports or hypothetical new reports.

5. Model security:

The saved model uses pickle-backed joblib. Only trusted local artifacts
must be loaded.

6. SQL Server deployment:

The current connection method is local Windows-oriented SQL Server. A
public application needs private network access, server-side secrets, a
least-privilege login, and likely a hosted database strategy.

7. Query abuse:

External users can trigger large scans, full downloads, repeated SARIMA
fits, and broad signal analyses unless limits, pagination, caching, and
timeouts are implemented.

8. Empty and sparse data:

Filtered groups may have zero reports, zero cells, or too few monthly
observations. The UI needs explicit empty-state and unavailable-metric
handling.

9. Statistical interpretation:

PRR/ROR are disproportionality measures, not incidence or causality.
The classifier predicts recorded seriousness labels, not clinical harm.
Forecast intervals are approximate residual-based intervals.

10. Documentation drift:

README.md still contains statements that ML and validated forecasting are
not implemented, although current source files and artifacts include them.

11. No application-level tests:

The current tests do not verify SQL joins, persisted model loading, or
web request behavior.

======================================================================
FINAL AUDIT CONCLUSION
======================================================================

The project has strong reusable analytical foundations, especially:

- SQL Server star-schema storage.
- Tested PRR/ROR calculation logic.
- Forecast model functions and backtesting.
- A persisted and preprocessing-complete classifier pipeline.

The missing layer is not the core analytics. It is the application
boundary:

- Safe parameterized queries.
- Report-grain aggregation.
- Interactive filtering.
- Model loading and prediction wrappers.
- Input validation.
- Limits, caching, and deployment controls.

The smallest maintainable implementation is:

1. Build reporting analytics services and tests first.
2. Add a Streamlit reporting page.
3. Add signal, forecasting, and classifier pages.
4. Harden deployment only after local workflows are verified.
