## 4. Audit the four interactive tools I want

My target application should contain these four tools:

### A. Drug safety signal explorer
Users should be able to enter or select a drug, reaction, date range if supported, and a minimum report-count threshold.

Expected outputs include report counts, PRR, ROR, confidence intervals, and signal-screening results where implemented.

Determine which calculations already exist, where they are implemented, their function signatures, and whether they can be called directly from an application.

### B. Reporting analytics dashboard
Users should be able to filter reporting data by supported dimensions such as dates, drug, reaction, country, and seriousness.

Expected outputs include report counts, serious-report proportions, monthly trends, and top drugs/reactions.

Identify existing SQL queries, aggregation functions, exports, and reusable logic. Do not assume every filter is currently supported.

### C. Reporting-volume forecasting
Users should be able to select a forecasting method and horizon where supported.

Expected outputs include historical trends, forecasts, uncertainty intervals where available, and backtesting metrics.

Identify the existing model implementations, input data format, required parameters, output format, saved artifacts, and limitations.

### D. Seriousness classifier
Users should be able to provide valid supported features and obtain the model's predicted recorded seriousness category and probability, if available.

Identify the saved model path, loading code, exact expected feature names and order, preprocessing steps, output labels, probability support, and validation metrics.

Never describe this as predicting whether a drug will harm a patient. It predicts the recorded report label if that is what the model was trained to predict.

For each tool, classify its current state as:
- Implemented and reusable
- Partially implemented
- Not implemented
- Cannot verify

Support the classification with file paths and function names.
