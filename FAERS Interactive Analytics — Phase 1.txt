Act as a senior Python data engineer and analytics application developer. Implement only the first incremental phase of my existing FAERS adverse drug event analytics project.

I have completed Stage 8, including SQL Server warehousing, statistical signal detection, forecasting, a persisted seriousness classifier, Power BI exports, and focused validation tests.

I want to build a web-accessible Streamlit application for myself and external users. Preserve the existing project and its working functionality.

## Confirmed product decisions

Use these decisions as requirements:

- Reporting date: FAERS `receivedate`, represented by the appropriate warehouse date key.
- Country filter: primary-source country, using `fact_report.country_key` and its associated country dimension.
- External access: aggregate statistics only. Do not expose individual report records, company numbers, or other report-level identifiers in this phase.
- Classifier workflow: users will select an existing report in a later phase. Do not implement classifier serving now.

Implement a reliable reporting analytics service and focused automated tests. Do not build the Streamlit interface in this phase.

### Step 3 — Implement reporting analytics

Create `services/analytics_service.py`, unless an equivalent service already exists.

Implement a function following this general interface, adapting types and conventions to the actual repository:

`get_reporting_summary(*, start_date=None, end_date=None, drug_name=None, reaction_name=None, country_code=None, serious_only=None, limit=100)`

Supported filters:

- Start date and end date using the chosen `receivedate` definition.
- Drug name using the existing normalized drug dimension and appropriate report-to-drug relationship.
- Reaction name using the existing reaction dimension and report-to-reaction relationship.
- Primary-source country using `fact_report.country_key`.
- Seriousness using `fact_report.is_serious`.
- A bounded result limit.

Return aggregate results with a predictable structure containing:

- Applied filter metadata.
- Total distinct report count.
- Distinct serious report count.
- Serious-report percentage, or null when its denominator is zero.
- Monthly report counts and serious-report counts.
- Top drugs and their distinct report counts.
- Top reactions and their distinct report counts.
- Any other aggregate-only output that can be justified by the existing schema.

Do not return individual report rows, report IDs, safety report IDs, company numbers, or identifying row-level details.

#### SQL correctness requirements

- Use `COUNT(DISTINCT fact_report.report_key)` or equivalent report-grain logic where required.
- Never sum a report-level seriousness flag after a raw many-to-many join of drug and reaction facts.
- Prefer `EXISTS`, distinct report-key subqueries, or correctly pre-aggregated queries when filtering by drugs and reactions.
- Apply all requested filters consistently to the numerator, denominator, monthly series, top drugs, and top reactions.
- Calculate the serious percentage from the filtered distinct report counts.
- Use `receivedate` semantics consistently.
- Whitelist any dynamic sorting fields and enforce the result limit in SQL or through a safe bounded mechanism.
- Handle NULLs, empty results, invalid date ranges, and invalid limits clearly.
- Do not assume that existing views accept parameters; inspect them and use suitable parameterized SELECT statements if needed.

Document whether drug/reaction filters use exact matching, normalized matching, or search matching. Choose behavior supported by the existing dimension data and make it predictable.

### Step 4 — Add focused automated tests

Add tests under the existing `tests/` structure, following repository conventions.

At minimum, test:

1. No filters returns the expected aggregate structure.
2. Start and end dates are passed correctly to SQL.
3. Drug, reaction, and primary-source country filters are applied.
4. Serious-only filtering behaves correctly.
5. Distinct report counts do not inflate when reports contain multiple drugs or reactions.
6. Serious percentages use the correct filtered denominator.
7. Empty results return safe values rather than crashing.
8. Invalid date ranges and out-of-range limits are rejected.
9. SQL values are passed as parameters rather than interpolated into query strings.
10. Connections and cursors are cleaned up after success and exceptions.
11. Aggregate-only responses contain no report-level identifiers or individual records.

Use mocks, fixtures, or small synthetic data for unit tests. Do not require production SQL Server access for ordinary unit tests.

If a test requires SQL Server integration, mark it separately and document the required environment. Do not claim an integration test passed if it was skipped or not run.
