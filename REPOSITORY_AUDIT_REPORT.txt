FAERS ADVERSE DRUG EVENT ANALYSIS
REPOSITORY AUDIT AND WEB APPLICATION READINESS REPORT

Report date: October 27, 2026
Repository: Adverse-Drug-Event-Analysis

======================================================================
1. EXECUTIVE SUMMARY
======================================================================

The project is a working FAERS analytics pipeline through Stage 8, but
it is not yet a web application.

The existing project already provides the core analytical capabilities
required for the planned application:

1. Drug safety signal detection using PRR, ROR, confidence intervals,
   and chi-square.
2. Reporting analytics through SQL Server views, generated JSON metrics,
   and Power BI CSV exports.
3. Reporting-volume forecasting using seasonal-naive, ETS, and SARIMA
   models with rolling-origin backtesting.
4. Seriousness classification using a persisted scikit-learn pipeline.

The smallest maintainable next step is to add a Streamlit application
that calls reusable Python functions and reads from the existing SQL
Server database. There is currently no API, frontend, or application
entry point to reuse.

No files were modified, no packages were installed, no ingestion was
executed, and no database changes were made during this audit.

3. FILE-BY-FILE PROJECT MAP
======================================================================

CORE PIPELINE
-------------

src/ingest.py
Purpose: Streams FAERS JSON data from a ZIP file into staging tables.
Main function: ingest().
Inputs: FAERS ZIP path.
Outputs: stg.reports, stg.drugs, stg.reactions.
Dependencies: ijson, pyodbc, python-dotenv.

Purpose: Cleans and validates staging data.
Main functions: _parse_date(), _age_to_years(), _quarantine(), clean().
Inputs: SQL Server staging tables.
Outputs: Cleaned staging data, quarantine records, quality logs.
Dependencies: pyodbc, pandas.

src/transform.py
Purpose: Converts staging data into the warehouse star schema.
Main functions: _get_or_create_date(), _get_or_create_country(),
_get_or_create_drug(), _get_or_create_reaction(), transform().
Inputs: stg.* tables.
Outputs: dbo.dim_* and dbo.fact_* tables.

statistics.
Inputs: SQL Server facts and views.
Outputs: results/stats.json.

src/pareto.py
Purpose: Calculates 80/20 Pareto summaries.
Main function: pareto().
Inputs: SQL query results.
Outputs: results/pareto.json.
Dependencies: pyodbc.

Purpose: Calculates receipt-to-receive reporting lag.
Inputs: Staging report dates.

Inputs: fact_report, dim_date, and staging dates.

IMPORTANT CLASSIFIER LIMITATION
--------------------------------

The classifier currently has a training workflow, but it does not have
a dedicated application-facing function such as:

    predict_seriousness(user_input)

The existing run() function loads all features, retrains models, logs
new MLflow runs, and saves the model. It should not be called every time
an external user submits a prediction request.

The web application should load the persisted joblib model once and
call predict() and predict_proba().

Current state: Partially implemented, with reusable core calculations.

Implemented function:

    calculate_signal(
        pair_count: int,
        drug_total: int,
        reaction_total: int,
        total_reports: int

It calculates:
- 2x2 table cells
- PRR
- PRR confidence interval
- ROR
- ROR confidence interval
- Yates-corrected chi-square

SQL-backed function:

    run(top_drugs: int = 100, min_pair_count: int = 3)

It:
- Connects to SQL Server.
- Selects top suspect drugs.
- Reads candidate drug/reaction pairs.
- Applies minimum pair-count filtering.
- Applies PRR >= 2 and chi-square >= 4.
- Writes results/signals.json.

Reusable:

- Date-range filtering.
- Direct pair lookup.

RELIABILITY CONCERNS
--------------------

1. Classifier prediction interface is missing.

The saved model exists, but no tested function loads it and performs a
prediction from external input. This is the most important gap for the
planned application.

2. Statsmodels convergence warning.

The statsmodels logistic model reported a convergence warning. Some
categorical levels are sparse or separated. Its odds ratios and confidence
intervals should not be presented as definitive user-facing findings.
The scikit-learn production pipeline is the better candidate for serving
predictions.

3. Feature semantics issue.

The classifier uses drug_count, suspect_drug_count, and reaction_count.
These are available at prediction time only if the user provides enough
information to calculate them.

The application must choose between:
- A structured report-input form.
- Selecting an existing report from SQL Server.
- A separate simplified model with fewer features.

This is a product decision and should not be assumed.

4. Forecasting is not fully interactive.

The forecasting script reads a precomputed trend file and runs a fixed
batch workflow. It does not support arbitrary date filters or method
selection from a web interface.

5. Signal filtering is partly fixed.

The workflow uses:
- pair_count >= 3
- PRR >= 2
- chi-square >= 4

The pair-count threshold can be passed through the command line, but PRR
and chi-square thresholds are fixed in the function.

6. No SQL query safety layer exists for external users.

An application needs:
- Parameterized filters.
- Whitelisted sort fields.
- Query limits.
- Pagination.
- Timeouts.
- Empty-result handling.
- Safe user-facing errors.

7. No external deployment configuration exists.

There is no verified:
- Docker image.
- Cloud database.
- Hosted SQL Server.
- Secret manager.
- TLS configuration.
- Authentication.
- Rate limiting.
- Monitoring.
- Health endpoint.

8. RECOMMENDED APPLICATION ARCHITECTURE
======================================================================

OPTION 1: STREAMLIT
-------------------

Advantages:
- Smallest implementation effort.
- Good fit for data-science workflows.
- Calls Python functions directly.
- Easy charts, filters, tables, and downloads.
- No separate frontend framework is required.
- Suitable for an initial controlled external demonstration.

Disadvantages:
- Not a traditional API layer.
- Fine-grained authentication is more difficult.
- Database connections need careful handling.
- Long-running queries can block sessions.
- Multiple users can create concurrent database load.
- Training code must not run during user requests.

Fit for this repository:
Best first option because the repository has Python analytics modules,
SQL Server access, a persisted model, and no existing API or frontend.

OPTION 2: EXISTING API/BACKEND
------------------------------

No existing API or backend was found. This option is not currently
available without creating a new backend.

A future FastAPI backend would be stronger for:
- External users.
- Authentication.
- Multiple frontends.
- API consumers.
- Clear request/response contracts.
- Background jobs.
- Rate limiting.

It requires more new structure than Streamlit.

OPTION 3: EXISTING FRONTEND
---------------------------

No existing frontend was found. This option is not applicable to the
current repository.

RECOMMENDATION
--------------

Use Streamlit as the first web application, with a small service layer.
Keep the analytical functions independent of Streamlit.

Suggested architecture:

app.py
    |
    v
UI and input validation
    |
    v
Service functions
    |
    +--> signal service
    +--> analytics service
    +--> forecast service
    +--> classifier service
    |
    v
Existing src modules
    |
    v
SQL Server / saved model / generated results

Streamlit should handle:
- User inputs.
- Input validation.
- Charts.
- Tables.
- Downloads.
- Session state.
- User-facing errors.

Service functions should handle:
- SQL queries.
- Signal calculations.
- Forecast execution.
- Model loading and prediction.
- Result serialization.

11. DEPLOYMENT CONSTRAINTS
======================================================================

SQL SERVER ACCESS
-----------------

The current project expects direct access through:

    SQLSERVER_CONNECTION

For deployment:
- Keep SQL Server on a private network.
- Do not expose the database directly to the public internet.
- Store credentials in a server-side secret manager.
- Use a restricted database login.
- Parameterize all queries.
- Add query timeouts and result limits.

Do not put SQL Server credentials in:
- Streamlit UI code.
- Git.
- Client-side JavaScript.
- Public configuration.
- Downloaded files.

MODEL ARTIFACT SECURITY
-----------------------

The classifier artifact uses pickle serialization. Pickle can execute
code during deserialization. Load the joblib artifact only from a trusted,
controlled location:

    results/model/seriousness_classifier.joblib

EXPENSIVE QUERY RISKS
---------------------

External users could trigger expensive operations through:
- Large date ranges.
- Large drug/reaction combinations.
- Full fact-table downloads.
- Repeated SARIMA forecasts.
- Large signal scans.
- High-cardinality groupings.

Recommended controls:
- Maximum date range.
- Maximum rows.
- Pagination.
- Query timeouts.
- Cached common queries.
- Restricted forecast horizon.
- Limited signal candidate count.
- Download size limits.
